# Vivarium

一个格子世界里的生命沙盘——你铺下材质、放下自己编辑基因的生物，然后松手，看它们自己长成没人设计过的样子。

**当前状态：M3 进行中** — 世界网格、材质流动（沙塌 / 水流 / 气浮 / 火蔓延）、多线程调度、
**活着的生物**（细胞占格、代谢、行为网络、进食、繁殖、死亡 → 残骸）、
两个渲染器与窗口前端均已可用。

**细胞现在看得见了**：放大之后能看出圆角带膜、按功能上色、同一条鱼的细胞连成一整块。
但身体还是三格——放大之后就是三个圆。渲染层已经准备好，缺的是**身体怎么来**。

生物会在**水平环面**上移动（从右边出去、从左边回来），种群的代数与基因漂移
已经可以观测（12000 tick 跑出 65 代）。但**还没有真正的选择压力**——
目前的基因漂移是中性的，不是适应。

---

## 这是什么

不是"一个有生命的游戏"，而是一个**会自己长出生命的盒子**。三条参考血统：

| 血统 | 代表作品 | 借什么 |
|---|---|---|
| 上帝沙盒 | WorldBox、The Powder Toy | 画笔式神力、灾害工具 |
| 进化模拟 | LifeEngine、The Bibites | 无设计的自然选择、形态自发演化 |
| 物质物理 | Noita、Evolving-Protozoa、ALIEN | 材质规则表、GRN 形态发生 |

刻意**不含**文明 / 王国 / 历史事件层。

## 世界的形状

**横板侧视剖面，有且只有一个重力方向（向下）。** 默认地貌是**海洋 + 岛屿**——大片水体，
散布几座岛屿，生物默认水生。

```
┌──────────────────────────┐
│  天空（约 30%）           │  ← 光从上往下射入，随深度衰减
├──────────────────────────┤
│  水体（约 36%）           │  ← 生物的主舞台：沙会沉、气会浮
├──────────────────────────┤  ← 水面线
│  基岩 / 沉积层（约 34%）  │
└──────────────────────────┘
             ↓ 重力
```

这个决定一次锁死三件互锁的事，所以它必须先定：

| 被它决定的东西 | 后果 |
|---|---|
| 材质规则 | 液体「下 → 左右」、气体「上 → 左右」、固体不动 |
| 更新顺序与并行 | 「自下而上扫描」+ 棋盘 4 相位（同相位分块互不相邻），都是为重力方向设计的 |
| 进化层难度 | 侧视下重力对所有生物都是负担——所以生物默认生活在水里 |

**为什么不是俯视（WorldBox 式）**：俯视下运动容易演化得多，但落沙层会退化成「涂格子」——
沙不会塌、水只能靠水位字段横向摊平，而且没有光梯度。材质层是这个项目的半个乐趣，不能丢。

**光梯度是侧视白送的机制**：生产者细胞必须待在浅水，而浅水正是掠食者的猎场。
垂直位置于是成为真实的生态位。

生成器在 `crates/core/src/worldgen.rs`（`sea_and_islands`）。

## 材质会动

七种材质（空 / 石 / 沙 / 水 / 火 / 气 / 残骸）各自只有**一张属性表**，
规则引擎只负责"按表执行"——加一种材质不需要动模拟循环的任何一行。

| 材质 | 行为 |
|---|---|
| 沙 / 残骸 | 向下落，斜着滑，**不横向找平** → 自然堆成 45° 休止角 |
| 水 | 向下落，斜着滑，被挡住就横向找平（一次最远探查 8 格） |
| 气 / 火 | 倒过来的液体：向上浮、向两侧扩散 |
| 火 | 12 tick 寿命；按可燃度概率点燃邻居；遇水熄灭 |

让路判定只有一条：**更重的挤开更轻的**。"目标必须是空或流体"保证沙丘能立住；
而**上浮不需要单独的规则**——气体顶不开水，但水能沉进气体里，
气泡上浮的真实机制是"上面的水塌下来"。

### 两个不显眼但必须写对的细节

**液体找平必须紧跟一次下落。** 最直觉的"侧邻空着就走"会让相邻两列水位 2/1
互相甩锅、**永远抖动**。后果不是"看起来有点晃"，而是分块脏标记永远清不空，
整个跳块优化直接失效。判据改成"目的地脚下必须能让开"之后，液面只能停在
"相邻列高度差 ≤ 1"——这正是离散网格上"平"的定义。

**世界之外不是空位。** `World::get` 对越界坐标返回 `Empty`（画笔拖到边缘时不该 panic），
但移动判定不能继承这个宽松。漏掉这条，浮到世界顶端的那层气会认为自己还能上浮，
沿着天花板左右滑动永不停歇。而且它只在真实地貌里显形——
人工搭的测试场景里没有那一层气。

> 这两个 bug 都归到同一类：**世界永远静不下来**。
> 它必须是一条测试契约，不是观感问题——一旦不成立，
> SPEC §2.4 的整个性能前提就没了。

## 世界是环形的（只对生物）

**左右边界首尾相接**：鱼从右边出去、从左边回来。材质层仍然是硬边界——
水不会从左边流出去又从右边流回来，因为材质层的分块并行依赖"两块之间至少隔一整块"
这个几何前提，一旦环绕就得把相位划分整个重做。

这条不是装饰。只给"往右"偏置的手工鱼会全部游到右边界堆成一团，
被领地规则卡住，种群停在 9 条——**表面看是生态平衡，实际是"所有鱼叠在一个角落"**。

环绕之后它们会自己散开，同时也暴露了一个更深的假象：局部遮挡和领地这两道负反馈
都是"位置相关"的，鱼一散开就同时失效，种群从 240 条涨到 **1737 条**。
所以补了第三道、也是唯一一道全局负反馈——**环境容纳量**：
生产者越多，每个分到的光越少。三道叠加，种群才真的稳在两百多条。

## 死掉的会烂掉

饿死的鱼留下的尸体没有能量，鱼不会去吃它，于是它只会在海底越堆越厚——
实测 12000 tick 后残骸占掉世界 6%。规则是**周期性的全局清扫**：
没有能量的残骸泡在水里，每 50 tick 有 20% 概率溶解掉。

为什么是"溶解"而不是"矿化成沙"：沙不会消失，转化只是把问题换个名字——
实测 20000 tick 后沙从 2826 格涨到 32052 格，占掉世界 12%。
**在一个没有出河口的封闭世界里，任何"转化"都会让某种材质单调累积。**
这条链上真正要守的是能量，不是格子数。

天然碎屑不会烂（`flags` 非零），所以没有生物的世界依然能完全静止。

## 生物会活

一格要么是材质，要么属于某个有机体的某个细胞——**不能同时是两者**。
这条互斥规则由一张与材质表并列的占格表执行，材质层只读它（`World::yields_to`）：
细胞格的材质字段永远是 `Empty`，如果材质层只看材质，水会灌进鱼肚子里。

一条最小的鱼是三格：**移动 + 嘴 + 生产者**。

| 细胞 | 干什么 | 每 tick 成本 |
|---|---|---|
| 生产者 | 把光转成能量，是唯一的"环境 → 生物"入口 | 5 |
| 移动 | 提供位移，没有它哪儿也去不了 | 4 |
| 嘴 | 吃邻格残骸 | 2 |

**活着很贵，而且光不够就活不下去。** 光从顶端射入、随深度线性衰减，
所以生产者必须待在浅水；深水里同样的鱼几十 tick 就饿死。
这条梯度是"生物为什么要浮上来"的全部理由。

**能量账是严格守恒的，并且可以直接断言**：

```
Σ 有机体身上的能量 + Σ 残骸蕴含的能量 + 累计耗散 == 累计注入
```

注入 = 太阳能 + 初始投放；耗散 = 维持成本 + 移动 + 死亡时的零头。
残骸的能量存在材质的 `flags` 里，所以残骸沉降、被水冲走时能量跟着走。
512² 跑 8000 tick、两百多条鱼生生死死，这条式子的差额是 **0**。

**行为是一张小网络**：12 路输入（前方有没有食物/阻挡/同类、四向阻挡、
能量比例、年龄比例、朝向）→ tanh 隐藏层 8 → 6 路输出（左右上下 / 吃 / 繁殖）。
手工鱼的基因组是写死的，只做三件事：往前游、撞墙折返、看到尸体就吃、攒够能量就生。
**M2 到此为止——还没有任何东西在进化。**

### 一个不显眼但必须写对的细节

**生物占的水要被挤开，不是被清掉。** 出生时直接 `set(Empty)` 会让海平面
随出生次数一点点下降——480 次出生吞掉 600 多格水。搬运顺序也有讲究：
必须**先占格再推水**，否则刚腾空的身体格会被当成"附近的好位置"，
水又被换回肚子里，鱼死后那格变成残骸，水就凭空没了。

> 这一类 bug 的共同点：**跑 100 tick 完全正常，跑 8000 tick 世界变了样。**
> 所以生态测试必须长跑，而且要断言"水总量逐格不变"这种硬指标。

## 快速开始

需要 Rust stable 与 MSVC 工具链（Windows）。

```bash
# 图形前端：开窗，看像素画面
cargo run --release -p vivarium-game

# 没有 GPU 或没有显示器时，在终端里跑同一套内核
cargo run -p vivarium-game -- --ascii

# headless 模拟并打印 ASCII 视图
cargo run -p vivarium-sim -- --width 256 --height 256 --ticks 1000 --ascii

# 在最高的岛顶点一把火，每 500 tick 报一次进度
cargo run --release -p vivarium-sim -- --ticks 3000 --ignite 40 --report-every 500

# 在水面附近放 20 条鱼，看它们游、吃、生、死
cargo run --release -p vivarium-sim -- --ticks 3000 --fish 20 --report-every 500

# 指定材质层的并行工人数（默认 0 = 自动）
cargo run --release -p vivarium-sim -- --ticks 1000 --threads 4

# 查看全部参数
cargo run -p vivarium-sim -- --help

# 测试
cargo test --workspace
```

窗口里的操作：`空格` 暂停/继续 · `1/2/3/4` 速度 · **滚轮 缩放 · 方向键 平移 · `0` 回到全景** ·
`F` 点火 · `L` 放鱼 · `R` 重铺地形 · `Esc` 退出。
也可以一开始就带着鱼启动：`cargo run --release -p vivarium-game -- --fish 40`。

**想看清细胞，把窗口开小一点再放大。** 512² 的世界塞进 1100 px 的窗口是 2.1 px/格，
一条三格鱼总共 6×2 像素——不是渲染坏了，是采样率不够。两个办法：

```bash
# 让世界变小，同样的窗口就有了 8.6 px/格
cargo run --release -p vivarium-game -- --width 128 --height 128 --fish 20
```

或者直接滚轮放大到十几倍。窗口标题里那个 `px/格` 就是当前密度。

`vivarium-sim` 不依赖任何图形库，可以在没有显示器的机器上跑长测。
它的报告里有四个比 hash 更该盯的数字：**活跃块数**（世界平静后应当掉到 0）、
**材质变化表**（守恒出问题时直接告诉你是哪种材质多了或少了）、
**工人数**（这一跑实际用到了几个线程），以及
**能量账的差额**（只要不是 0，就说明有一条能量通道没走记账点）。

## 打包

每完成一版都打一次包，产物是**双击就能跑的单文件 exe**（不需要装 Rust、不需要装任何运行库）：

```powershell
.\scripts\package.ps1              # → dist\vivarium.exe
.\scripts\package.ps1 -IncludeSim  # 顺带打包 headless 模拟器
```

`dist\VERSION.txt` 记录这一份是哪个 commit 构建的。`dist/` 不入库——
仓库里只有源码和这个脚本。

打包完记得**试运行一次**：编译通过不等于 exe 能跑，wgpu 的适配器初始化
只有在真的开一次窗口之后才知道成不成。

### 想看一眼渲染结果

不用开窗口，直接把离屏渲染导成 PNG：

```bash
cargo test -p vivarium-render --lib -- --ignored --nocapture render_preview_png
# → target/render-preview.png          刚生成的地貌
# → target/render-preview-settled.png  材质层跑完之后的同一张图
# → target/render-preview-life.png     放鱼并跑 300 tick 之后

# 放大看细胞：一个近景、一个全景
cargo test -p vivarium-render --lib -- --ignored --nocapture render_preview_cells
# → target/render-cells-close.png      17 px/格，看得到膜、融合、按功能上色
# → target/render-cells-wide.png       zoom 3，看地貌与鱼群分布
```

像素渲染的 bug（颜色偏了、上下颠倒、留边错位）几乎都是"看一眼就知道、
但很难写好断言"的那一类。三张图能一次覆盖全部像素，而它们的**差异**
就是"材质规则和生命层真的在工作"最直观的证据。

第三张还钉住一件容易写错的事：细胞格的材质字段永远是 `Empty`，
如果脏块检测只看材质，鱼在水里游的时候渲染器会认为什么都没变，画面上一条鱼也没有。

近景那张另外钉住一条：**同一条鱼的细胞必须连成一块，不能有接缝**。
这条在 CPU 侧完全看不出来（键都写对了），只有真的把像素读回来量接缝亮度才发现——
第一版融合逻辑写对了，但明暗用了到格边界的距离，格边界处亮度归零，
身体于是又被切回一颗颗糖。

## 项目结构

```
crates/
  core/    模拟内核：材质、材质流动（含并行调度）、细胞与有机体、生命层调度、
           网格分块、确定性随机、地貌生成  ← 零依赖
  render/  Renderer trait + ASCII 渲染器 + wgpu 像素渲染器
           （`shaders/blit.wgsl` 里做 SDF 细胞形状、融合、按功能上色）
  ui/      面板与检查器（占位）
  app/     主循环、输入、时间控制
bins/
  sim/     headless 模拟器
  game/    图形前端（winit 事件循环）
```

地貌生成刻意放在 `core` 而不是各个 bin 里：M0 期间它被复制了三份
（sim / game / 渲染预览测试），三份已经开始漂移。世界形状是**设计决定的载体**，
不该有互相矛盾的实现。

## 三条架构约束

这几条不是风格偏好，是设计决定：

1. **`core` 不依赖任何渲染或窗口库。** 验证进化靠的是"跑几千上万代"，不是"盯着画面看"。
2. **`bins/sim` 刻意不依赖 wgpu / winit / egui。** 一旦它拉进图形依赖，每次编译多等几分钟，长跑调参就废了。
3. **`render` 不依赖 winit。** 它只接受一个已经建好的 `wgpu::Surface`——窗口是应用层的事，画像素不是。这样 headless 渲染不必拖进一整套窗口系统。

另外，`Renderer::render` 只接收 `&World`——"切换渲染器不改变模拟结果"这条验收断言，靠签名在编译期兜底。

## 渲染：脏块增量上传

世界纹理与世界同尺寸（512² 约 1 MiB），但**每帧只重传变过的 64×64 块**。

带宽其实不是瓶颈（1 MiB × 60 FPS = 60 MiB/s，GPU 不在乎）；
真正的成本是 CPU 侧的逐格转换——262144 个格子逐个算、逐字节写入。
分块之后，静止的块连这一步都省了。

这与 SPEC 第 2.4 节一致：落沙层的成本取决于**活跃格子比例**，不是网格大小。

按 `R` 重铺地形时，窗口标题里的"本帧上传"会瞬间跳到满格再掉回 0——
那就是增量逻辑在工作的直接证据。

## 纹理存的是语义，不是颜色

世界纹理是 `R32Uint`，每格一个键：

```
0x8000_0000 | (organism << 8) | cell_type
└─ 是细胞      └ 个体 id        └ 细胞类型
```

**颜色、形状、膜、轮廓光，全在 shader 里从键算出来。** 一开始的写法是 CPU 查调色板、
往纹理里写 RGBA——那意味着"这一格长什么样"在 CPU 侧就定死了，而 CPU 一格只能写一个颜色，
所以一格只能是一个方块。

想要圆角、想要同一条鱼的细胞连成一整块、想要膜在身体内部不出现、想要按功能而不是按个体上色，
这些全是**像素级**判断，只能在 shader 里做，而 shader 需要的是语义，不是颜色。

于是占格表多了一个 `kind: u8`（这一格是嘴还是生产者）——**不多占内存**，
`u32 + u16` 本来就要 padding 到 8 字节，白赚。之所以存在占格表而不是让渲染器去查生命层：
渲染器只拿得到 `&World`，为了知道"这是嘴"而让它持有整个 `LifeSim`，是把两层焊死。

### 融合不是"画粗一点"

同一条鱼的相邻细胞之间不该有缝。做法是**查四邻居**：同 `organism` 的一侧，把边界从格内
推到格外（`±0.5 → ±1.0`）。于是身体内部那几面墙根本不存在——边界是**从邻居关系推出来的**，
不是估出来的，所以身体形状换了会自动跟着变。

这里有一个只有把像素读回来才发现的坑：融合逻辑写对了，但明暗用了"到格边界的距离"，
而那个距离在格边界处正好归零。结果是**刚融合好的身体又被切回一颗颗糖**。
改成按"到格心的距离"算，融合处的亮度由两侧各自贡献，不会掉到零。

基础亮度也因此从 0.5 抬到 0.72：细胞边界处亮度本来就低，基础值再低，
两颗细胞相接的地方会暗到和水几乎同色，看起来像断成两截。

### 按功能上色，不按个体

嘴橙红、生产者绿、移动青蓝、眼黄、杀手紫红、装甲灰蓝、构造器琥珀。
这条是从 ALIEN 借的视觉语言：**看颜色就知道这格在干什么**。

按个体上色看起来更"丰富"，但它把注意力引到"这是谁"，而结构信息在"这是什么"。
一个身体要能看出结构，先得让同一种细胞在视觉上连成一片。

## 相机

`Viewport { center, zoom }`，属于渲染层，**不进世界哈希**——它改变的是"看哪里"，不是"发生了什么"。

滚轮缩放、方向键平移一成视口、`0` 回全景、`+`/`-` 快速缩放。窗口标题实时显示 `px/格`。

这个功能存在的理由只有一个：**512² 塞进 1100 px 的窗口是 2.1 px/格**，
一条三格鱼是 6×2 像素。在加相机之前，"看不到细胞结构"看起来像渲染 bug，
实际是采样率不够——`--width 128 --height 128` 一行就能零成本验证。

> 顺带一个调试陷阱：`ensure_world` 首次建纹理会把相机重置到世界中心。
> 离屏渲染测试里如果先设 viewport 再 `upload()`，重置会**静默覆盖**掉视口，
> 结果看起来像"细胞根本没画出来"——但键、shader、绑定全是对的。
> 修法是先 upload 再设 viewport，并且只在世界尺寸真的变了时才重置。

## 可复现性

所有随机走固定种子的 PCG 发生器（手写、零依赖），禁用系统随机。
契约：**同种子 + 同操作序列 ⇒ 同结果**，网格哈希逐 tick 一致。

```bash
cargo run -p vivarium-sim -- --quiet --seed 42 --ticks 1000 | grep hash
```

材质层每格每 tick 要做的随机决策（往哪边滑、这一格点不点得着）走的是
**位置派生**随机数 `Rng::at(x, y, tick, salt)`，而不是上面那个顺序推进的 RNG。
理由不是性能，是**可验证性**：共享的顺序 RNG 会让"哪些格子先被处理"变成世界状态的一部分，
于是并行化和跳块扫描都成了无法验证的赌博。

换成位置派生之后，"跳块扫描"与"每 tick 全网格扫描"给出**逐格相同**的结果，
这条性质是直接写成测试的（`skipping_static_chunks_matches_a_full_scan`）。
并行也是同一回事：`--threads 1` 与 `--threads 16` 逐 tick 哈希相同
（`thread_count_does_not_change_the_world`）。

但**扫描顺序本身**是这个世界定义的一部分。分块按棋盘相位分组是并行的前提，
而分组必然改变"谁先被处理"——把顺序改掉，同一个种子会长出另一个世界
（物理结果不变，具体排布会变）。所以有一条黄金哈希测试
（`the_scan_order_is_part_of_the_world`）钉住它：以后谁动扫描顺序，它会立刻红。

### M1 实测

| | |
|---|---|
| 512² 满负载（沙雨传送带）1 线程 | **3.44 ms/tick** |
| 512² 满负载 8 线程 | **1.59 ms/tick（2.16x）** |
| 512² 满负载 自动档（落在 8 工人） | **1.65 ms/tick** |
| 512² × 20,000 tick（真实地貌，绝大部分时间静止） | **146 ms**（0.0073 ms/tick） |
| 世界静止所需 | **221 tick**（此后活跃块恒为 0，每 tick 访问 0 格） |
| 测试 | 136 个全绿 · clippy 零警告 |
| 跳块 vs 全扫 | 400 tick 逐 tick 逐格哈希相同 |
| 线程数 vs 结果 | 1 / 2 / 4 / 8 / 16 线程，逐 tick 哈希相同 |

**多线程已经接上了**，而且不是"能跑就算"：分块先拷进私有副本、规则只在副本上跑、
相位之间由主线程顺序写回，所以线程之间没有任何共享的可变状态——
"线程数不影响结果"是构造上成立的，不是靠多跑几次碰运气。

调参用 `--threads N`，默认 0 = 自动（按本机核数与当 tick 活量收敛）。
注意**不是线程越多越快**：建一个线程约 30 µs，所以 `--threads 16` 在这台机器上
反而比 8 慢——自动档就是为了避开这件事。

### M3 实测（观测已接上）

| | |
|---|---|
| 512² × 12000 tick，8 条起步 | 种群 305、**最大代数 65**、平均代数 44.1 |
| 与初代的基因距离 | **0.171** |
| 平均能量 | 235（没有随代数上升 → **中性漂移**） |
| 性能 | 1.30 ms/tick |

**基因距离在涨，但平均能量没有跟着涨。** 这是"漂移"而不是"适应"：
现在的选择压力只回答"你能不能活着"，不回答"你活得比邻居好吗"。

加上 `IN_LIGHT` 输入（鱼能感知自己在多深）与播种时的个体差异之后：

| | 之前 | 之后 |
|---|---|---|
| 基因距离 | 0.171 | **0.195** |
| 平均能量 | 235 | **271** |

**两者同步上升了**——这是"适应"的初步信号。幅度不大，因为现在的世界
对"聪明"几乎没有奖励：只要不游到深海就能活。

### M3 实测（渲染层）

| | |
|---|---|
| 测试 | **191 个全绿**（core 151 · render 36 · app 4）· clippy 零警告 |
| 窗口实测 | 512² + 30 条鱼，420 fps |
| 纹理格式 | `R32Uint` 语义键，CPU 侧从"查表写 RGBA"变成"拼一个整数" |
| 看得见细胞所需的密度 | ≥ 10 px/格（`--width 128` 或 `zoom ≥ 5`） |

**这一轮最重要的结论不是代码，是诊断**：之前以为"看不到细胞结构"是渲染没做对，
实际是 2.1 px/格 的采样率根本画不出结构。先量一下像素密度，能省掉一整轮瞎猜。

### M2 实测

| | |
|---|---|
| 512² + 240 条鱼（材质层 + 生命层） | **1.07 ms/tick** |
| 种群规模 | 8 条起步，2000 tick 内涨到 250 上下，之后在 220–280 之间波动 |
| 能量账 | 8000 tick 后差额 **0** |
| 水总量 | 8000 tick 内**逐格不变** |
| 测试 | 176 个全绿 · clippy 零警告 |

种群规模由两道负反馈决定：**光被上方生物遮挡**（密处更穷）与
**领地限制**（附近同类超过 6 个就不繁殖）。只有前者时种群会指数爆炸，
只有后者时所有鱼会叠成一团、卡在 9 条。
